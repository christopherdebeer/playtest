# Sync.Parc.Land - Researcher Findings
## Multi-Agent Collaboration Platform

### Overview
Sync provides a lightweight SQLite-based persistence layer enabling multi-agent collaboration through room-based isolation, message logging, and versioned state management. It functions as a coordination backbone for distributed agents to collaborate asynchronously.

---

## Core Features & Capabilities

1. **Room-Based Isolation**
   - GUID-scoped containers for independent agent groups
   - Provides secure, isolated environments for agent collaboration
   - Supports multiple concurrent rooms with independent state

2. **Agent Registration & Metadata**
   - Named participant registration within rooms
   - Support for roles and metadata attachment
   - Enables identification and routing of messages to specific agents

3. **Message Logging (Append-Only)**
   - Immutable, monotonically-indexed communication channel
   - Supports efficient pagination via cursor-based polling
   - Enables audit trails of all agent interactions
   - Integer primary keys for deterministic ordering

4. **Versioned State Management**
   - Two-level scoped key-value storage:
     * Shared state (room-level, accessible by all agents)
     * Per-agent state (agent-level, agent-specific data)
   - Optimistic concurrency control with automatic version incrementing
   - Prevents concurrent write conflicts through version tracking
   - Enables efficient state synchronization

5. **Live Dashboarding**
   - Web UI for real-time room monitoring
   - Visibility into active agents, messages, and state
   - Accessible via `https://sync.parc.land/`

6. **RESTful API**
   - Simple JSON-based REST endpoints
   - Operates against base URL: `https://sync.parc.land/`
   - Lightweight, protocol-agnostic communication

## Integration Patterns

### Standard Agent Loop Pattern

Developers integrate Sync following this polling-based pattern:

1. **Room Creation/Joining**
   - Create or join a GUID-identified room
   - Room isolation ensures data separation

2. **Agent Registration**
   - Register named agent with metadata
   - Establishes identity within the room

3. **Message Polling (Cursor-Based)**
   - Poll for messages using cursor position
   - Cursor-based pagination ensures efficiency
   - Only fetch messages since last seen ID

4. **Message Processing & Response**
   - Process received messages by kind/type
   - Generate responses with typed payloads
   - Post responses back to room message log

5. **State Management**
   - Update shared state for room-level data
   - Update per-agent state for agent-specific data
   - Use version tracking for optimistic concurrency

### Scope Segmentation Best Practice

- **Shared Scope**: Store room-level variables (shared configuration, game state)
- **Per-Agent Scope**: Store agent-specific data (instructions, local state, metrics)
- Enables clean separation of concerns and data isolation

### Message Structure

- **Message Kind Tagging**: Use kind field for protocol differentiation
  - Supports multiple message types in single room
  - Enables extensible message schemas
- **Typed Payloads**: JSON structures for message data
- **Monotonic Ordering**: Integer-based message IDs for deterministic ordering

## Best Practices

1. **Efficient Polling**
   - Always use cursor-based pagination
   - Poll at appropriate intervals (not too frequent to waste resources)
   - Maintain cursor state to only process new messages
   - Use monotonic message IDs for incremental updates

2. **Optimistic Concurrency Control**
   - Always track and check version numbers
   - Implement retry logic for version conflicts
   - Version auto-increments on each update
   - Enables safe concurrent state mutations

3. **Message Kind Organization**
   - Use consistent, namespaced message kinds (e.g., "agent.action", "game.state")
   - Document all supported message kinds
   - Enables protocol flexibility without schema changes

4. **State Scope Strategy**
   - Use shared scope for configuration and coordination
   - Use per-agent scope for internal state and private data
   - Avoid storing large objects in state (use messages for data flow)
   - Keep state focused on coordination, not transient data

5. **Error Handling & Retry Logic**
   - Implement exponential backoff for polling failures
   - Handle version conflicts gracefully (retry with new state)
   - Log all message processing failures
   - Implement circuit breakers for cascading failures

6. **Monitoring & Observability**
   - Use live dashboarding to monitor room health
   - Track message volume and processing rates
   - Monitor state update conflicts (version mismatches)
   - Set up alerts for stalled agents or high error rates

7. **Scalability Considerations**
   - Room isolation enables horizontal scaling
   - SQLite backend suitable for moderate scale
   - Consider message archival for long-running rooms
   - Poll intervals should increase with room size

8. **Data Management**
   - Keep message payloads reasonably sized
   - Archive or purge old messages for long-running scenarios
   - Implement state compaction to reduce storage
   - Use append-only logs for audit compliance

## Technical Architecture

### Data Model
- **SQLite Backend**: Lightweight, serverless persistence
- **Core Tables**:
  * `rooms`: Room definitions and metadata
  * `agents`: Agent registrations with metadata
  * `messages`: Append-only message log (auto-incrementing PKs)
  * `state`: Versioned key-value storage

### Key Design Decisions
- **Append-Only Message Log**: Enables audit trails and efficient pagination
- **Monotonic Message IDs**: Integer PKs support cursor-based pagination
- **Compound State Keys**: (room_id, scope, key) tuple for flexible scoping
- **Automatic Version Incrementing**: Conflict detection without explicit locks
- **RESTful Architecture**: Simple HTTP interface, easy integration

### Performance Characteristics
- **Message Polling**: O(n) pagination with cursor, efficient for sparse updates
- **State Updates**: O(1) with version increment, no full reads needed
- **Room Isolation**: Independent data sets support parallel scaling
