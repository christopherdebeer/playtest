## DATABASE SCHEMA & DATA MODEL
================================================================================

SCHEMA OVERVIEW:
The system uses SQLite as the backing storage with four primary tables:

1. ROOMS TABLE
   - Primary Key: id (GUID)
   - Fields: created_at, meta
   - Purpose: GUID-keyed containers that isolate agent groups
   - Isolation Model: Each room maintains independent namespace
   - Metadata: Custom metadata can be attached per room

2. AGENTS TABLE
   - Primary Key: id (agent_id)
   - Foreign Key: room_id (references rooms.id)
   - Fields: name, role, joined_at, meta
   - Purpose: Named participants with assigned roles in specific rooms
   - Scoping: Agent IDs used for per-agent state isolation
   - Registration: Agents join/register to rooms with identity tracking

3. MESSAGES TABLE
   - Primary Key: id (monotonically increasing integer)
   - Foreign Key: room_id (references rooms.id)
   - Fields: from_agent, to_agent, kind, body, created_at
   - Message ID Sequencing: Integers increment monotonically
   - Append-Only Pattern: Immutable once written
   - Ordering Guarantee: Sequential IDs enable efficient polling

4. STATE TABLE
   - Composite Primary Key: (room_id, scope, key)
   - Fields: value, version, updated_at
   - Versioning: Auto-increments on every write
   - Scope Levels: Two-tier hierarchy
     * _shared: Room-wide state accessible to all agents
     * Agent IDs: Per-agent isolated state
   - Version Strategy: Integer counter for optimistic concurrency detection

DATA MODEL CHARACTERISTICS:
- Compound Primary Keys: State uses (room_id, scope, key) preventing duplicates
- Timestamp Tracking: updated_at field for audit trail
- Metadata Fields: Both rooms and agents support custom meta objects
- Message Routing: Supports directed messages via from_agent/to_agent
- Kind Tags: Message classification (message, task, result, event, error)

## MESSAGE SYSTEM DETAILS
================================================================================

MESSAGE PROTOCOL:
The append-only message log forms the primary communication backbone:

WRITE OPERATIONS:
- Endpoint: POST /rooms/:id/messages
- Payload: { body, kind? }
- Operation: Appends to monotonically-increasing ID sequence
- Atomicity: Single write operation maintains sequence integrity
- Response: Returns assigned message ID

READ OPERATIONS:
- Endpoint: GET /rooms/:id/messages?after=<id>&kind=<type>&limit=<n>
- Cursor-Based Pagination: Uses `after` parameter to fetch messages after ID N
- Kind Filtering: Optional message type filtering (message, task, result, event, error)
- Limit: Configurable batch size for polling efficiency
- Ordering: Always ascending ID order guaranteed

MESSAGE ID SEQUENCING:
- Type: Monotonically increasing 32/64-bit integers
- Uniqueness: Never reused within room scope
- Ordering: Ensures causality and temporal ordering
- Efficiency: Enables range queries without timestamp parsing

POLLING PATTERN (Standard Workflow):
1. Agent stores highest message ID observed locally
2. On next poll: GET /rooms/:id/messages?after=stored_id
3. Receives only new messages with IDs > stored_id
4. Updates local high-water mark
5. Repeats efficiently without redundant data transfer

CHARACTERISTICS:
- Immutable Log: Messages never modified or deleted
- Complete History: All messages retained indefinitely (per current docs)
- No Transactions: Individual message appends are atomic
- No Ordering Guarantees Within Payload: Kind filtering happens client-side

MESSAGE ROUTING:
- From/To Fields: Support directed communication between specific agents
- Broadcast Pattern: to_agent=null or wildcard patterns implied
- No Queue Depth: All agents see all messages in room
- Race Conditions: Possible in concurrent message processing

## STATE MANAGEMENT & VERSIONING
================================================================================

STATE ARCHITECTURE:
The two-level scoped state store enables both shared and isolated coordination:

VERSIONING SYSTEM:
- Mechanism: Auto-incrementing version counter on every write
- Optimistic Locking: Version serves as concurrency detection flag
- Conflict Detection: Client can compare versions before/after writes
- No Built-In Resolution: Clients must handle version conflicts
- No Locking: No distributed locks or exclusive access control

SCOPE MANAGEMENT:
1. ROOM-WIDE STATE (_shared scope)
   - Visibility: All agents in room can read/write
   - Use Case: Shared configuration, game state, coordination state
   - Access Pattern: PUT /rooms/:id/state { scope: "_shared", key, value }
   - Concurrency: Any agent can write; last-write-wins on same key

2. PER-AGENT STATE (agent_id scope)
   - Visibility: Owner agent + potentially other agents with explicit queries
   - Use Case: Personal memory, agent-specific config, private data
   - Access Pattern: PUT /rooms/:id/state { scope: agent_id, key, value }
   - Isolation: Reduces contention and coordination overhead

STATE OPERATIONS:
- PUT (Update/Insert): /rooms/:id/state { scope, key, value }
  * Returns new version number
  * Auto-increments version on write
  * Default scope: _shared when unspecified
  * Upsert semantics: Creates if not exists

- GET (Query): /rooms/:id/state?scope=X&key=Y
  * Returns: { value, version, updated_at }
  * Supports filtering by scope and key
  * Returns current version for concurrent reads
  * Read-only operation (no side effects)

- DELETE (Remove): /rooms/:id/state { scope, key }
  * Removes entry entirely
  * Returns success/failure status
  * No tombstones (truly deleted)

COORDINATION PATTERN:
1. Agent reads state with current version: GET /rooms/:id/state?scope=_shared&key=turn
   Response: { value: 0, version: 5 }
2. Agent computes new state: { value: 1, version: 6 }
3. Agent writes state: PUT /rooms/:id/state { scope: _shared, key: turn, value: 1 }
4. If concurrent write occurred, version mismatch indicates conflict
5. Agent must retry or implement custom conflict resolution

LIMITATIONS:
- No Conditional Writes: No CAS (Compare-And-Swap) semantics documented
- No Transactions: State writes are not atomic across multiple keys
- Version is Information-Only: No automatic conflict resolution
- Client Responsibility: Agents must implement conflict handling logic

## CONCURRENCY CONTROL
================================================================================

OPTIMISTIC LOCKING IMPLEMENTATION:
The system relies on optimistic concurrency control through versioning:

MECHANISM:
- Version Field: Integer counter incremented on state writes
- No Blocking: No locks acquired during reads or writes
- Conflict Detection: Clients observe version changes
- Detection Method: Compare version before/after read-modify-write cycle
- Cost: Low latency, high throughput; conflicts must be handled by client

CONFLICT SCENARIO EXAMPLE:
1. Agent A reads: state = { value: 5, version: 10 }
2. Agent B reads: state = { value: 5, version: 10 }
3. Agent A writes new value 6, receives version: 11
4. Agent B writes new value 7, receives version: 12 (overwrites A's change)
5. Result: Lost update on Agent A's modification
6. Detection: Agent A must track expected versions to detect this

RESOLUTION STRATEGY (Not Documented):
- No automatic conflict resolution provided
- Last-write-wins: Implicit strategy when versions not checked
- Client-Driven: Applications must implement strategies like:
  * Retry with exponential backoff
  * Undo and reapply logic
  * Custom application semantics
  * Consensus-based resolution

ISOLATION LEVELS:
- Message Reads: Read-Committed (monotonic progression)
- State Reads: Read-Uncommitted (may see dirty writes)
- Multi-Key Atomicity: Not supported
- Dirty Reads: Possible if not checking versions

RACE CONDITIONS & SAFETY:
- Message IDs: Monotonic integer generation prevents collisions (safe)
- Agent Registration: Multiple joins with same agent_id may conflict (unsafe)
- State Updates: Concurrent writes to same key cause silent overwrites (unsafe)
- Multi-Agent Coordination: Requires application-level consensus

SCALABILITY IMPLICATIONS:
- Contention on Shared State: High agent count writing to _shared scope
- Version Number Overflow: Theoretical issue with unlimited version increments
- SQLite Locking: Serialized write access to SQLite database (bottleneck)

## DURABILITY & PERSISTENCE
================================================================================

PERSISTENCE MODEL:
The system uses SQLite's ACID properties with application-level design:

ACID ANALYSIS:

ATOMICITY:
- Single Row Operations: Individual message inserts are atomic
- State Updates: Single state key writes are atomic
- No Multi-Row Atomicity: No transactions spanning multiple rows
- Append-Only Safety: Message IDs guaranteed unique and sequential

CONSISTENCY:
- Schema Consistency: SQLite maintains schema invariants
- Foreign Key Integrity: room_id references enforced (if enabled)
- State Consistency: Version auto-increment prevents age-old writes
- No Application Consistency: No enforcement of business logic invariants

ISOLATION:
- SQLite Serialization: Write operations serialize at database level
- Read-Committed Messages: Message polling sees consistent snapshots
- Dirty Reads Possible: State updates may be partially visible
- No Snapshot Isolation: Concurrent reads of state may see different versions

DURABILITY:
- SQLite Persistence: Data written to disk (journal/WAL)
- Crash Recovery: SQLite recovery on restart
- No Explicit Fsync: Write-Ahead Logging (WAL) mode implied
- Synchronous Writes: Likely using "NORMAL" or "FULL" synchronous setting

PERSISTENCE GUARANTEES (Inferred from SQLite):
- Committed Writes: Persisted to disk before operation returns
- Crash Consistency: Database recoverable after unclean shutdown
- Durability Window: Brief window between memory write and disk flush
- No Replication: Single database file, no redundancy documented

RECOVERY MECHANISMS:
- Automatic Recovery: SQLite auto-recovery on open after crash
- WAL (Write-Ahead Logging): Likely enabled for better concurrency
- Crash Loop Protection: No documented mechanisms
- Data Corruption Handling: No documented repair procedures

BACKUP & DISASTER RECOVERY:
- No Documented Backups: System docs don't mention backup strategy
- No Replication: Single-node SQLite only
- Manual Backup: Required to copy SQLite database file
- Recovery Time: Depends on backup frequency
- Point-in-Time Recovery: Not supported
- Geographic Redundancy: Not available

DATA RETENTION:
- Append-Only Messages: Never deleted (infinite retention default)
- State Overwrite: Updates erase previous values
- Soft Deletes Not Used: DELETE operations truly remove entries
- No Archival: No documented cold storage or archival process

## TECHNICAL TRADE-OFFS & DECISIONS
================================================================================

DESIGN CHOICE: SQLITE BACKEND
Trade-off: Simplicity vs. Scalability
- Pro: Lightweight, zero-configuration, ACID guarantees, embedded
- Con: Single-writer bottleneck, not distributed, limited concurrency
- Implication: Suitable for moderate-scale agent coordination, not high-throughput
- Alternative: Would require PostgreSQL/MySQL for horizontal scaling

DESIGN CHOICE: MONOTONIC MESSAGE IDs
Trade-off: Simplicity vs. Distributed Consensus
- Pro: Guaranteed ordering without distributed consensus
- Con: Requires single authoritative ID generator
- Implication: SQLite auto-increment simplifies implementation
- Alternative: Would need sequence number protocol (Lamport clocks, etc.)

DESIGN CHOICE: OPTIMISTIC VERSIONING WITHOUT CAS
Trade-off: Client Simplicity vs. Consistency
- Pro: No blocking, clients can detect conflicts
- Con: Lost updates possible without careful application logic
- Implication: Requires sophisticated conflict handling in agents
- Alternative: Would use Compare-And-Swap or pessimistic locking

DESIGN CHOICE: TWO-LEVEL STATE SCOPING
Trade-off: Flexibility vs. Complexity
- Pro: Supports both shared and per-agent coordination patterns
- Con: Agents must understand scoping semantics
- Implication: Applications need careful state organization
- Alternative: Could use single shared namespace or pure per-agent

DESIGN CHOICE: APPEND-ONLY MESSAGES
Trade-off: Immutability vs. Storage
- Pro: Guarantees message history, enables efficient polling
- Con: Disk space grows unbounded, no message editing
- Implication: Long-running rooms accumulate large message logs
- Alternative: Would need message deletion/archival policies

DESIGN CHOICE: NO DISTRIBUTED LOCKING
Trade-off: Performance vs. Coordination
- Pro: Avoids deadlocks and lock management complexity
- Con: Requires pessimistic conflict avoidance by agents
- Implication: Race conditions possible in poorly-designed protocols
- Alternative: Would use leader election or consensus (Raft, etc.)

DESIGN CHOICE: POLLING-BASED MESSAGE DELIVERY
Trade-off: Simplicity vs. Latency
- Pro: Stateless server, easy client implementation, no connection management
- Con: Latency proportional to polling interval
- Implication: Real-time responsiveness limited by poll frequency
- Alternative: Would use WebSocket push or event streams

DESIGN CHOICE: KIND TAGS WITHOUT ORDERING
Trade-off: Flexibility vs. Semantics
- Pro: Supports diverse message types
- Con: Kind filtering happens client-side; no priority guarantee
- Implication: Applications must implement kind-specific processing
- Alternative: Would separate queues by kind or use message priority

## ARCHITECTURAL PATTERNS & IMPLICATIONS
================================================================================

ISOLATION MODEL:
- Room-based Isolation: Complete separation between collaboration groups
- No Cross-Room Communication: Agents must explicitly bridge rooms
- GUID Room IDs: Naturally unique without coordination
- Implication: Simple multi-tenancy model

AGENT COORDINATION PATTERNS:
- Centralized Message Log: All communication flows through room log
- No Direct Agent-to-Agent: Communication requires message intermediary
- Broadcast by Default: Messages visible to all room agents
- Implication: Suitable for turn-based or controlled coordination

SCALABILITY LIMITS:
- Single SQLite File: Entire room history in one database
- Write Serialization: Messages and state writes serialize at database
- Room Fan-Out: All agents poll same message log
- Implication: Practical limit ~1000s of agents per room

STATE MANAGEMENT COMPLEXITY:
- Distributed State: Agents maintain partial replicas locally
- Eventual Consistency: State becomes consistent as agents process
- Stale State Risk: Agents may act on outdated state snapshots
- Implication: Applications must be designed for eventual consistency

FAILURE MODES:
- Database File Corruption: No automatic recovery beyond SQLite journal
- Lost Messages: If database corrupted before flush to disk
- Incomplete Consistency: If agent crashes mid-coordination
- Recovery Manual: Human intervention may be needed for severe failures

## KEY FINDINGS SUMMARY
================================================================================

STRENGTHS:
- Minimal, focused API surface (6 core operations)
- Strong ACID guarantees from SQLite
- Monotonic message IDs guarantee causality
- Room-based isolation provides natural multi-tenancy
- Two-level state scoping supports diverse coordination patterns

WEAKNESSES:
- No built-in conflict resolution mechanism
- SQLite write serialization limits concurrency
- Append-only messages cause unbounded storage growth
- No distributed replication or failover
- Polling introduces coordination latency
- No cross-room communication primitives

SUITABLE FOR:
- Small to medium-scale agent coordination (10-1000 agents)
- Turn-based game playtesting with multiple agents
- Prototyping multi-agent systems quickly
- Isolated collaboration sessions with defined lifetime

UNSUITABLE FOR:
- High-throughput message streams (>1000 msgs/sec)
- Real-time responsiveness requirements (<100ms latency)
- Large-scale distributed systems (>10k agents)
- Long-term archival with unbounded message growth
- Cross-region or geo-distributed coordination

PRODUCTION CONSIDERATIONS:
- Implement message archival/retention policy
- Monitor SQLite file size growth
- Design application-level conflict resolution
- Test failure modes and recovery procedures
- Consider backup/restore strategy
- Plan for scaling beyond single database
